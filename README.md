# Приём оплаты дополнительных образовательных услуг — ИУБиП

Одностраничная форма оплаты через СБП (Альфа-Банк, динамический QR-код).
Студент заполняет данные, читает оферту, подтверждает согласие на обработку
персональных данных, сканирует QR — платит из приложения своего банка.

Реализовано по официальной документации Альфа-Банка «Динамический QR-код»:
`GetQRCd`, `GetQRCstatus`, `qrc/notification`.

## Что уже работает

- Форма: ФИО, телефон, группа, сумма. Валидация на клиенте **и** на сервере.
- Окно оферты — обычным текстом с прокруткой. Галочка акцепта неактивна,
  пока текст не дочитан до конца.
- Отдельный документ согласия на обработку ПДн (п. 4.7 оферты, 152-ФЗ).
- Сумма проверяется на минимум **500 ₽** — дважды, на клиенте и на сервере.
- Собственный генератор QR без внешних зависимостей (для демо-режима и офлайн-показа).
- Журнал платежей с выгрузкой CSV для бухгалтерии.
- Вебхук под финальный статус оплаты.

## Демо-режим

По умолчанию `CONFIG.MODE = 'stub'`: QR строится локально из данных формы,
платёж не проводится, деньги не двигаются, наружу ничего не уходит.
Так страницу можно показывать и тестировать без банка. Именно в этом режиме
работает публикация на GitHub Pages — там сервера нет.

## Запуск

```
node server/index.js
```
Откроется на `http://localhost:3000`.

### Проверки

```
node test/verify.js          — валидация, сборка запроса GetQRCd, таблицы QR
node test/server-smoke.js    — HTTP-слой, защита от обхода каталога
node test/sweep-all.js       — генерация 27 QR во всех версиях и уровнях
python test/decode-opencv.py — чтение этих QR камерой (OpenCV)
```

Последние два — самые важные: они проверяют то же, что делает камера
телефона. Требуется Python с `opencv-python`.

`node test/verify.js` — 205 проверок.
`node test/server-smoke.js` — 20 проверок.
Декодирование камерой — 27 из 27.

## Что нужно от Альфы

Без этого боевой режим не запустится.

1. **Авторизация.** В присланном разделе документации её нет: описан формат
   запросов, но не подпись, не сертификат и не заголовки. Запросить раздел
   про авторизацию у менеджера банка.
2. **`TermNo`** — идентификатор терминала.
3. **URL шлюза** и режим (`ALFA_GATEWAY_URL`).
4. **Тестовый стенд** и тестовый `TermNo` — чтобы проверить до продакшена.
5. **Письмо на `acquiring@alfabank.ru`** с запросом настройки реестра СБП.
   Без него `extJsonParams` (ФИО и группа) в выгрузку не попадут — код при
   этом будет работать и ошибок не покажет.

## Переменные окружения

```
PORT=3000
ALFA_GATEWAY_URL=https://<шлюз Альфы>
ALFA_TERM_NO=<TermNo>
PUBLIC_BASE_URL=https://<домен с публичным HTTPS>
ALFA_AUTH_HEADER=<значение заголовка авторизации>
ALFA_AUTH_SCHEME=header|bearer|basic
ALFA_QRC_TYPE=02
ALFA_QR_TTL=30
MIN_AMOUNT=500
PURPOSE_TEMPLATE=Оплата за {fio}, группа {group}, доп. образовательные услуги
```

**Ключи мерчанта не бывают в браузере.** Они читаются сервером из окружения.
Фронтенд ходит только в `/api`.

## Переключение в боевой режим

В `config.js`:

```js
MODE: 'live',
TERM_NO: '<TermNo>',
NOTIFICATION_URL: 'https://<домен>/api/webhook/alfa',
```

## Важные ограничения — прочитать до запуска

**Сумма 500 ₽ — наша проверка, а не банковская.** В `GetQRCd` минимальной
суммы нет: Альфа примет 300 ₽ без единого возражения. Если убрать проверку,
оплата пройдёт ниже минимума.

**ФИО плательщика из QR не придёт.** В ответах Альфа отдаёт только `payerId` —
маскированный телефон. Причём это телефон того, кто платит: если платит
родитель, а не студент, будет родительский. Привязывать оплату к студенту
по `payerId` нельзя.

**Отсюда архитектура:** источник правды о том, кто и за что платил — наш
журнал `data/orders.json`. Туда пишутся ФИО и группа в момент создания
платежа. Альфа подтверждает факт, сумму и время. Если реестр СБП не
настроен или 1С его не читает, данные всё равно останутся у нас, а
полученное от банка сверяется с нашим по `qrcId`, `trxId` и сумме.

**Что увидит бухгалтерия — вопрос к договору, а не к коду.** Код передаёт
назначение платежа и `extJsonParams`. Дойдут ли они дальше в выписку или
в 1С, определяется настройкой на стороне банка. **Проверяется только тестовой
оплатой**: заполнить ФИО «Тестовый Тест Тестович», группой «ГР-99»,
оплатить 500 ₽ и попросить выгрузку. Нет строки — не работает, сколько ни
обещали на встрече.

**Персональные данные.** ФИО и телефон — ПДн по 152-ФЗ. Согласие
собрано галочкой, но нужно ещё прописать сроки хранения и удаление после
закрытия договора. `data/orders.json` в публичный репозиторий не выкладывается.

## Установка в Bitrix

Статика, без сборки и зависимостей. Папку положить в раздел сайта.
Файлы: `index.html`, `style.css`, `config.js`, `offer.js`, `alfa-sbp.js`,
`validation.js`, `qr-renderer.js`, `app.js`.

Если раздел открывается по другому пути и серверного бэкенда там нет —
оставьте `MODE: 'stub'`. Боевой режим требует домена с HTTPS, доступного
из интернета: туда Альфа будет присылать `notificationUrl`.

## Структура

```
index.html               страница
style.css                оформление
config.js                единственный файл для правок при внедрении
offer.js                 текст оферты и согласия на ПДн
validation.js            правила заполнения полей
alfa-sbp.js              адаптер Альфы: GetQRCd, GetQRCstatus, webhook
qr-renderer.js           генератор QR (только демо-режим)
app.js                   логика страницы
assets/iubip-logo.svg    логотип с сайта iubip.ru
server/index.js          прокси к шлюзу, журнал платежей, вебхук, CSV

```

Шапка повторяет сайт iubip.ru: логотип, название, горячая линия,
приёмная комиссия, кнопка «Заказать звонок», основное меню. Логотип
взят с сайта — `https://iubip.ru/local/templates/univer/img/logo.svg`.

## Что проверено

`node test/verify.js` — 205 проверок: назначение платежа и лимит 140 символов,
формат `SenderFIO`, нормализация телефона, суммы в копейках, границы суммы,
состав запроса `GetQRCd`, сверка таблиц блоков коррекции с эталоном
ISO/IEC 18004, детерминированность генератора.

`node test/server-smoke.js` — 20 проверок: отдача статики, блокировка обхода
каталога (`../`, percent-кодирование, доступ к `data/` и `server/`),
серверная валидация полей, приём вебхука с лишними полями, выгрузка CSV.

`python test/decode-opencv.py` — 27 из 27 QR прочитаны декодером OpenCV,
включая кириллицу и все четыре уровня коррекции.

В браузере вручную пройден полный сценарий: заполнение полей → блокировка
кнопки → прокрутка оферты → разблокировка галочки → обе галочки → создание
QR → отображение ФИО, группы, суммы и номера заказа. Проверено также, что
кнопка блокируется при сумме 499 ₽, без одной из галочек, при недопустимом
ФИО и без заполненных полей.

### Найденные и исправленные ошибки генератора QR

Генератор написан с нуля, потому что страницу встраивают в Bitrix, где
внешний CDN может быть недоступен. Первая версия выдавала QR, которые
**выглядели правильно, но не читались камерой**. Нашёл это только
декодированием, а не просмотром:

- неверный форматный идентификатор уровня коррекции (взят полный
  15-битный код вместо 5-битного);
- байты заполнения `EC/11` добавлялись после сборки кодовых слов;
- маски не откатывались при выборе лучшей, матрица накапливала искажения;
- при равных блоках пропускались байты коррекции целиком;
- ошибки в таблице блоков для v19-Q, v20-Q и v19-H;
- отсутствовал индекс `-1` в таблицах, из-за чего все версии съезжали
  на единицу.

Урок: самопроверка генератора бесполезна — его логика совпадает с логикой
проверки. Единственная честная проверка — сторонний декодер.

## Не проверено

- **Реальный запрос к шлюзу Альфы** — настроек и ключей нет.
- **Авторизация** — раздел документации не получен.
- **QR от самого банка** — в демо-режиме код строит наш генератор;
  в боевом приходит готовое изображение в base64 от Альфы.
- **Приём оплаты** — невозможно без тестового стенда банка.
